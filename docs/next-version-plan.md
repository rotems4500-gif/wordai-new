# תוכנית לגרסה הבאה

## קו מנחה

לא נכון לדחוף את כל עשרת הסעיפים לאותה גרסה באותה רמת מחויבות. הגרסה הבאה צריכה קודם לייצב את מסלול היצירה והתיקונים, למנוע חיתוך מסמכים, לאחד את בחירת המודלים, ולמנוע מצבי תקיעה. כל מה שהוא תשתית עתידית או polish צריך להיכנס רק אם נשאר מרווח ביצוע אחרי סגירת ה-P0.

## P0

בנוסף, טיפול בייצוא Word עבור RTL ו-`he-IL` נשאר במעקב הקרוב של P0. בוצע כבר תיקון ראשון בתוך שני בוני ה-DOCX כך שברמת ה-section מוגדר `page.textDirection` יחד עם ברירות המחדל הקיימות של `bidirectional` ו-`he-IL`. אם אחרי התיקון הזה Word עדיין יפתח מסמך מיושר שמאלה, נקודת הבדיקה הבאה היא מסלול ההזרקה ל-Word/Office ולא בונה ה-DOCX עצמו.

### 4. טיפול בבעיה שהאפליקציה לפעמים "ננעלת" עד פתיחה מחדש

**מטרה:** למנוע מצב שבו בקשה נתקעת, ה-UI נשאר ב-loading, והמשתמש חייב לסגור ולפתוח את האפליקציה.

**שינוי טכני מומלץ:** להפעיל timeout ברירת מחדל ברמת orchestration ולא רק ברמת קריאות בודדות, לרכז את מחזור החיים של בקשה אחת במקום אחד ב-src/services/aiService.js, ולהבטיח שכל מסלול של create, review ו-revise עובר דרך finally שמנקה loading, submitting ו-live generation. בנוסף צריך כפתור התאוששות גלוי במסך הרלוונטי: ביטול בקשה, ניסיון חוזר, וניקוי מצב תקוע. ההיפותזה הסבירה כרגע היא שה-timeout קיים בקוד אבל כבוי כברירת מחדל, ולכן בקשה שנתקעת משאירה את מצב הטעינה דלוק.

**עדכון נוכחי:** נוסף כפתור recovery בפאנל ההרצה שב-sidebar כדי לנקות מצב תקוע או לסגור מצב שגיאה בלי לפתוח מחדש את האפליקציה.

**קבצים מרכזיים:** src/services/aiService.js, src/main.jsx, src/services/workspaceLearningService.js.

**סיכון:** timeout אגרסיבי מדי יפיל בקשות איטיות לגיטימיות; תיקון חלקי רק ב-UI יסתיר את הבעיה בלי לפתור את שורש התקיעה.

**קריטריון קבלה:** כאשר ספק לא מחזיר תשובה או נתקע, המשתמש מקבל הודעת timeout או abort, מצב הטעינה יורד בלי פתיחה מחדש, ואפשר להתחיל בקשה חדשה מאותו מסך.

### 5. תיקון רשימות המודלים של Gemini, כולל 2.5 Flash ו-2.5 Pro ובדיקה מול API key

**מטרה:** לבטל פיצול והבדלי התנהגות בין מסכים שונים, כך שאותם מודלים של Gemini יוצגו וייבדקו בצורה אחידה בכל האפליקציה.

**עדכון נוכחי:** `getProviderModelChoices` משמש עכשיו כ-source of truth ב-FileMenu, ב-StartScreen וגם ב-AiSidebar. ה-sidebar שומר override מקומי של provider/model, מעביר `modelOverride` גם לצ׳אט ישיר וגם להרצת role agents, ו-`chatWithRoleAgent` נותן קדימות ל-runtime model override מעל `agent.model` בלי לשבור את ברירת המחדל של הסוכן.

**שינוי טכני מומלץ:** להעביר את קטלוג המודלים ל-source of truth אחד ב-src/services/aiService.js, ולגרום ל-FileMenu, StartScreen ו-AiSidebar לצרוך רק אותו. כרגע רשימות Gemini מפוזרות ולא עקביות, ולכן יש סיכוי ש-2.5 Pro מופיע במקום אחד ולא במקום אחר. בבדיקת החיבור צריך לאמת לא רק שה-API key קיים, אלא שגם המודל שנבחר אכן זמין עבור אותו key, עם fallback לבדיקת generate קצרה אם list models לא זמין או לא אמין.

**קבצים מרכזיים:** src/services/aiService.js, src/FileMenu.jsx, src/StartScreen.jsx, src/AiSidebar.jsx.

**סיכון:** בדיקת key/model מול ה-API יכולה להוסיף latency ולהתנגש במכסות; אם משאירים hard-coded lists במסכים, הפיצול יחזור מהר.

**קריטריון קבלה:** Gemini 2.5 Flash ו-Gemini 2.5 Pro מופיעים בכל המסכים הרלוונטיים, נשמרים נכון בהגדרות, ונפסלים מראש עם הודעה ברורה אם ה-key לא תומך במודל שנבחר.

### 10. מניעת מצב שבו הסוכן חותך את המסמך באמצע

**מטרה:** להבטיח שביצירה, שכתוב ותיקון של מסמכים ארוכים, הפלט נשמר שלם והמודל לא מאבד את החצי השני של המסמך או מחזיר תשובה קטועה בלי חיווי ברור.

**שינוי טכני מומלץ:** קודם צריך לטפל בשורש הבעיה ולא רק בפלט. ההשערה הסבירה כרגע היא שבזרימות fix, ובכל מסלול שלא שומר full document context מקצה לקצה, ההקשר של המסמך עלול להיחתך לפני הקריאה למודל, כך שבמסמכים ארוכים המודל רואה רק את תחילת המסמך. בנוסף, במסלולי create יש סיכון משני של תקרת output בלי מנגנון continuation. לכן צריך: להפסיק להעביר מסמך מלא כ-string קצר חתוך, ולעבור ל-chunking או windowing מבוקר למסמכים ארוכים; להבחין בין context לצורך ניתוח לבין content שצריך להישמר בשלמותו; לבדוק finish reason או equivalent אצל כל provider; ולהוסיף continuation או segmented rewrite כשפלט ארוך נעצר לפני סיום. במסכים הרלוונטיים צריך גם חיווי ברור כשהפלט חלקי ולא 'הצלחה' מטעה.

**עדכון slice:** נחת continuation יחיד למסמכי HTML ב-create/revise לפני fallback; ההמשך האוטומטי נשען עכשיו גם על completion reason של provider במקרי length/max tokens ולא רק על HTML שבור. revise שומר עכשיו על ה-HTML המלא גם ב-direct וגם ב-workflow דרך `preserveFullDocumentContext`, וה-validator של HTML עודכן כך שלא יכשיל בטעות תגיות HTML5 עם optional end tags כמו `li`, `p`, `tr`, `td` ו-`th`. review נשאר עם head/tail gap כדי לא להרחיב scope; chunking מלא נשאר לסלייס המשך.

**קבצים מרכזיים:** src/services/aiService.js, src/services/workspaceLearningService.js, src/main.jsx, src/AiSidebar.jsx.

**סיכון:** תיקון שטחי רק של max_tokens יקטין מקרים מסוימים אבל לא יפתור אובדן הקשר במסמכים ארוכים; chunking לא נכון יכול לשבור HTML, כותרות ומבנה מסמך.

**קריטריון קבלה:** מסמך ארוך שעובר יצירה או תיקון נשמר שלם גם כאשר המקטע המבוקש נמצא אחרי אלפי תווים, ואם provider עוצר לפני הסוף המערכת ממשיכה אוטומטית או מציגה חיווי חלקי ברור ולא מחליפה את המסמך בפלט קטוע.

### 8. עוד סבב במסך התיקונים + בחירת אילו סוכנים ירוצו בו

**מטרה:** להפוך את מסך התיקונים ממסך של yes/no למסלול תיקון אמיתי עם סבב נוסף נשלט ובחירת גורמי הביצוע.

**שינוי טכני מומלץ:** להרחיב את feedbackSurvey/state ב-src/main.jsx כך שיכלול roundIndex, executionMode ו-selectedAgents, ולהפסיק לכפות forceDirectMode על כל מסלול התיקון. reviseDocumentWithFeedback ו-reviewDocumentRecommendations צריכים לקבל מצב ביצוע מפורש: direct, workspace agents, או subset של agents שנבחרו עבור סבב התיקון. צריך להגביל את זה לסבב נוסף אחד כברירת מחדל כדי לא לפתוח לולאה אינסופית, ולהציג למשתמש בחירה פשוטה: תיקון ישיר, תיקון עם סוכנים נבחרים, או המלצות בלבד.

**עדכון slice:** feedback survey שומר עכשיו `executionMode` ו-`roundIndex`, מציג בחירה פשוטה בין direct לבין workflow של צוות הסוכנים הפעיל, ומגביל את המסלול לשני סבבי תיקון מאותו flow. בנוסף תוקנה דליפת state בין מסמכים שונים. בחירת subset מפורש של agents עדיין נשארת לסלייס המשך.

**קבצים מרכזיים:** src/main.jsx, src/services/workspaceLearningService.js, src/AiSidebar.jsx, src/FileMenu.jsx, src/StartScreen.jsx.

**סיכון:** אם נעתיק את כל מורכבות בחירת הסוכנים למסך התיקונים, הוא יהפוך כבד ומבלבל; אם לא נגדיר cap ברור, תיווצר שרשרת תיקונים איטית ויקרה.

**קריטריון קבלה:** משתמש יכול לשלוח תיקון, לקבל תוצאה, ולבצע סבב נוסף אחד מאותו מסך עם בחירת subset של agents או direct mode, בלי לאבד הקשר ובלי לצאת מה-flow.

## P1

### 1. זיכרון להערות שחוזרות על עצמן בתיקונים ויישום אוטומטי שלהן

**מטרה:** לקצר תיקונים חוזרים ולהפוך הערות קבועות של המשתמש לכללי עבודה מתמשכים.

**שינוי טכני מומלץ:** לא נכון ליישם auto-learn חופשי על כל טקסט משוב. במקום זה צריך שכבת recurring feedback memory שמזהה הערות שחוזרות 2-3 פעמים, מציעה להפוך אותן לכלל קבוע, ושומרת אותן כמבנה מפורש: category, normalizedInstruction, hitCount, autoApplyEnabled, scope. את הכללים הפעילים צריך להזרים ל-review ול-revise דרך src/services/workspaceLearningService.js ו-src/services/aiService.js, אבל תמיד עם חיווי גלוי במסך התיקונים כדי שהמשתמש ידע מה הוחל אוטומטית ויוכל להסיר כלל בעייתי.

**קבצים מרכזיים:** src/services/aiService.js, src/services/workspaceLearningService.js, src/main.jsx, src/FileMenu.jsx.

**סיכון:** זיכרון אוטומטי אגרסיבי מדי ייצור memory poisoning ויכניס הוראות ישנות להקשרים לא נכונים; אם אין שקיפות, המשתמש יאבד אמון בתיקונים.

**קריטריון קבלה:** אחרי שהערה חוזרת אושרה כמה פעמים, המשתמש מקבל הצעה להפוך אותה לכלל קבוע, והכלל מוחל אוטומטית בתיקון הבא עם אפשרות כיבוי נקודתית וקבועה.

### 3. Developer Options למשתמשים מתקדמים

**מטרה:** לתת שכבת שליטה וכלי אבחון למשתמשים מתקדמים בלי לזהם את ה-flow הרגיל למשתמשים חדשים.

**שינוי טכני מומלץ:** לפתוח אזור Advanced סגור כברירת מחדל בתוך FileMenu או Settings, עם toggles מעטים אבל קריטיים: timeoutEnabled ו-requestTimeoutMs, force direct מול workflow, provider/model override, export/clear debug logs, appendAgentNotesToOutput, והפעלה של פיצ'רים ניסיוניים כמו visual generation shelf. זה צריך לשבת על מודל הגדרות אחד ב-src/services/aiService.js ולא על flags מפוזרים בלוקאל סטייט.

**קבצים מרכזיים:** src/FileMenu.jsx, src/services/aiService.js, electron/main.cjs.

**סיכון:** Developer Options פתוח מדי יגדיל עומס תמיכה ויאפשר למשתמשים לשבור לעצמם את ה-flow; אפשרויות שאין להן reset ברור ייצרו תקלות שקשה לשחזר.

**קריטריון קבלה:** משתמש מתקדם יכול להפעיל או לכבות flags מתקדמים ממקום אחד, ההגדרות נשמרות, ויש reset to defaults בלי צורך למחוק storage ידנית.

### 7. פתרונות למעבר לריפו פרטי ועדיין לשמור auto-update

**מטרה:** לאפשר הפרטה של קוד המקור בלי לשבור את מסלול ההפצה והעדכון האוטומטי של Electron.

**שינוי טכני מומלץ:** להחליט על אסטרטגיית update feed לפני מעבר הריפו לפרטי. אסור להטמיע GitHub token בתוך אפליקציית desktop כדי למשוך releases פרטיים. כרגע auto-update נשען בפועל על GitHub Releases ציבורי דרך electron/main.cjs, package.json ו-.github/workflows/publish-release.yml, ולכן המעבר חייב להפריד בין source repo לבין artifact feed. בנוסף, צינור ה-release צריך להתיישר במפורש ל-Node 24 מקצה לקצה: לעדכן את GitHub Actions, גרסאות ה-actions הרלוונטיות ושלבי ה-packaging/publish כך שיישארו תואמים ל-Node 24 ולמבנה ה-feed שנבחר בין private source לבין public artifacts.

| חלופה | מה משתנה | יתרונות | חסרונות | המלצה |
| --- | --- | --- | --- | --- |
| 1. ריפו קוד פרטי + ריפו הפצה ציבורי | ה-build נשאר בריפו פרטי, אבל release assets ו-latest.yml עולים לריפו ציבורי ייעודי | שינוי מינימלי באפליקציה, ממשיך לעבוד טוב עם GitHub Releases, מהיר ליישום | דורש שני ריפוז ותהליך publish נוסף | החלופה המעשית ביותר לגרסה הקרובה |
| 2. Generic provider על S3/R2/Cloudflare | autoUpdater עובר ל-feed חיצוני ו-artifacts עולים ל-object storage | מפריד לגמרי בין קוד להפצה, אין תלות ב-GitHub public repo | דורש הקמת bucket, הרשאות ו-pipeline חדש | ההמלצה לטווח בינוני אם רוצים שליטה תפעולית טובה |
| 3. שרת עדכונים פרטי עם signed URLs | האפליקציה פונה לשרת שלך שמחזיר manifest וקישורים חתומים | שליטה מלאה, אפשר להוסיף רישוי או phased rollout | הכי מורכב ויקר לתחזוקה, דורש backend אמיתי | לא לגרסה הקרובה אלא רק אם נכנסים למודל מסחרי מלא |

**קבצים מרכזיים:** electron/main.cjs, package.json, .github/workflows/publish-release.yml.

**סיכון:** מעבר חצי-אפוי לריפו פרטי ישבור בדיקת עדכונים ביום השחרור; אם feed URL ו-publish target לא יישבו על אותה אסטרטגיה, העדכון יישאר על גרסה ישנה בלי חיווי ברור.

**קריטריון קבלה:** ניתן להוציא build מריפו פרטי, לפרסם artifacts לפי החלופה שנבחרה, והאפליקציה המותקנת מזהה ומורידה עדכון בלי תלות בריפו קוד ציבורי.

## P2

### 2. אנימציות משמעותיות בפתיחה, בדף הבית וביצירת מסמך

**מטרה:** לשפר תחושת מוצר וזרימה בלי להסתיר latency אמיתי ובלי להעמיס על הביצועים.

**שינוי טכני מומלץ:** להגדיר motion language מצומצם ולא להוסיף אנימציות קוסמטיות אקראיות. שלוש האנימציות שבאמת שוות השקעה הן: כניסת אפליקציה ראשונה, reveal מדורג של ה-cards במסך הבית, ו-transition בין מצב "מייצר" למצב "המסמך נוצר". אם אפשר לבצע זאת עם CSS ו-state קיים, עדיף לא להוסיף ספריית אנימציה חדשה; רק אם צריך orchestration מורכב, לשקול ספרייה ייעודית. בכל מקרה חובה לכבד prefers-reduced-motion.

**קבצים מרכזיים:** src/StartScreen.jsx, src/main.jsx, קבצי ה-style של מעטפת האפליקציה.

**סיכון:** אנימציה לא מרוסנת תרגיש כמו מסך טעינה מזויף ותסתיר תקלות אמיתיות; תנועה מוגזמת תפגע במשתמשים רגישים ובמחשבים חלשים.

**קריטריון קבלה:** שלושת רגעי המפתח מקבלים אנימציה עקבית, מהירה וברורה, יש reduced motion, ואין עיכוב מורגש בזמני אינטראקציה.

### 6. יכולת עתידית ליצירה חזותית וגרפים "על המדף"

**מטרה:** להכין תשתית שניתן להדליק בהמשך עבור visual generation, בלי להעמיס על הגרסה הקרובה מנוע גרפי מלא.

**שינוי טכני מומלץ:** לא לבנות עכשיו engine אמיתי ליצירה חזותית. במקום זה צריך לייצר shelf architecture: חוזה אחיד ל-visual job, feature flag נסתר, ונקודת חיבור אחת שמסוגלת בעתיד להחזיר chart, diagram או image asset. כרגע יש חלקי תשתית בסיסיים בלבד כמו insertImage ותרשימי HTML פשוטים, ולכן הצעד הנכון הוא לייצב abstraction ולא להבטיח יכולת generation מלאה.

**קבצים מרכזיים:** src/main.jsx, src/Ribbon.jsx, src/DocumentEditor.jsx, src/services/aiService.js.

**סיכון:** אם מנסים להכניס visual generation אמיתי כבר עכשיו, זה יפתח scope של asset hosting, export, layout ו-provider support שאין לו מקום בגרסה הזו.

**קריטריון קבלה:** יש feature flag ותכנון API פנימי ברור ל-visual assets, ויש לפחות spike אחד נסתר שמדגים הכנסת asset חזותי דרך אותו צינור בלי לחשוף את הפיצ'ר לכל המשתמשים.

### 9. אימוג'ים וחיווי חזותי בהערות הסוכנים בסוף המסמך

**מטרה:** להפוך את נספח הערות הסוכנים לקריא ומהיר לסריקה, בלי להפוך אותו לצעקני או ילדותי.

**שינוי טכני מומלץ:** לנצל את ה-builder הקיים של agent notes appendix ב-src/services/aiService.js, ולהוסיף שכבת presentation קלה: badge או emoji עקבי לכל role, חיווי נפרד ל-open gaps, והבדלה ברורה בין manager summary, readiness signal והערות סוכן. ב-DOCX או plain text צריך fallback טקסטואלי נקי כדי לא לפגוע ביצוא.

**קבצים מרכזיים:** src/services/aiService.js.

**סיכון:** אם מגזימים עם אימוג'ים, המסמך יאבד רצינות, במיוחד בהקשרים אקדמיים או משפטיים; אם אין fallback טוב, הייצוא ל-DOCX ייראה שבור.

**קריטריון קבלה:** כשהנספח פעיל, כל הערת סוכן מקבלת badge עקבי, open gaps בולטים מיד לעין, והיצוא ל-DOCX נשאר קריא גם בלי עיצוב HTML עשיר.
